The problem

Pickup football runs on group chats — and breaks there

In Indonesia, a weekly mini-soccer game is organised in a WhatsApp group. The organiser counts heads by scrolling, collects fees by bank transfer, and screenshots the receipts. When someone drops out on Friday night, the slot is resold in the chat — and whether the replacement actually paid is anyone's guess.

The product's job is to absorb that entire workflow. That makes it far less a social app than it first appears: the hard parts are capacity, money, and state. Who holds which position, who has paid, by when, and what happens automatically when they don't.

The constraint that shaped everything: Indonesian amateur sport runs on direct bank transfer, not card rails. No payment processor was in scope. The system therefore had to model an out-of-app payment it cannot observe — proof upload, human verification, deadlines and automatic expiry — rather than simply reading a webhook.

Request path, top to bottom.

One rule keeps the backend maintainable: the route files don't make decisions. A route's only job is to read the incoming request and send a response back. The real work — pricing a slot, working out when an unpaid spot expires, transferring a booking to another player — lives in its own module that knows nothing about the web: it never touches Express, it just takes values in and returns values out. Those modules hold the logic; the routes are a thin layer on top.

It earns its keep whenever a feature needs a second caller:

  • Admin override on slot resale. The transfer logic was already independent of the request, so adding an admin path was a branch on permission — not a second implementation of the transfer.
  • Shared payment deadlines. Meets and memberships computed expiry by identical rules; that resolution is now one unit-tested module both call, so the calculation deciding whether someone keeps their spot has a single definition, not two copies drifting apart.

Hard problems

Two that took real thought

1 · Selling a slot when the platform can't see the money

A player who can't make Saturday should be able to sell their spot. But payment happens by bank transfer, outside the system entirely. The platform can never confirm funds moved — so it has to make the humans confirm it, while preventing the obvious abuses: double-selling one slot, or a buyer claiming a spot and never paying.

1

Seller lists a confirmed slot pending

Only a slot they actually hold, on a meet that hasn't started.

2

Buyer claims it claimed

The oldest listing is claimed first, the slot is reserved against other buyers, and only now are the seller's bank details revealed.

3

Buyer pays out of app, uploads proof pending_review

The transfer receipt is stored as evidence for a human to judge.

4

Seller or club admin decides completed

Acceptance transfers slot ownership atomically. Rejection releases the claim and returns the listing to the pool — it does not strand it.

Escrow without an escrow provider.

The admin override in step four is the detail that makes it usable. Sellers go quiet; without a second party who can accept, a paid buyer would be stuck indefinitely.

2 · Position-aware capacity

"Twelve players" is not a useful description of a football match. The system models capacity per role and position category, drawn from one shared vocabulary covering football, futsal and mini soccer:

anygkdef midattuniversal futsal-gkanchorwinger pivot

A recent refactor pushed this further: the participant management UI was rebuilt to derive its options entirely from backend capacity data, so adding a role or position on the server surfaces in the interface with no frontend change. That deleted a 614-line configuration component outright.

Status & what's next

Offline for now — and the roadmap from here

The hosted beta is paused. Firebase Hosting still serves the frontend, so the site loads; the Cloud Run API behind it no longer starts, so sign-in fails and nothing past the login screen is reachable. The cause is billing rather than code — the same wall the mini-erp case study runs into, an Indonesian debit card that neither Google nor Stripe will verify. Nothing was rolled back and nothing broke; the service simply stopped being paid for. Bringing it back is a redeploy, not a repair.

Everything described above was built and working in production, and the screenshots are from that deployment while it was serving real users. The work I'd prioritise when it returns, in order:

  • Harden the diagnostic surface. A handful of development-only endpoints need locking down before general availability. First on the list.
  • Automated tests around money. The domain logic was deliberately written free of Express so it can be tested directly. That affordance exists and hasn't been spent yet; the resale and payment state machines are where it should go first.
  • Finish the settings screen. The privacy API is already live and consumed elsewhere — this is UI work against a working backend.
  • Scheduler off the request path — endpoint built, deploy pending. The membership lifecycle ran only on an in-process timer, which stops when the service scales to zero. It now also runs behind a secret-protected job endpoint, so an external trigger (Cloud Scheduler) can advance it on a fixed cadence regardless of traffic; the in-process timer stays as a warm-container fallback. What remains is wiring the Scheduler job in the cloud console.
  • Observability. Console logging is the current answer. Structured logs and error tracking are the gap between beta and something you'd run on call.
Consolidated since: the grace-period deadline — the rule that decides when an unpaid spot expires — had been copied almost line-for-line between meets and memberships. It now lives in one shared, unit-tested resolver both delegate to, verified behaviour-identical, so a money-critical rule has exactly one definition instead of two that could drift. (Slot resale is a claim-then-confirm flow with no deadline, so it stays separate by design rather than being forced under the same roof.)

Backend case study · solo build

A multi-tenant ERP where isolation is the database's job, not the code's.

mini-erp runs procurement, inventory and finance for more than one company out of a single deployment. Every tenant-scoped query executes inside a transaction that has told PostgreSQL who is asking, and fourteen tables carry a row-level security policy that returns nothing when it hasn't been told. The feature that pays for that architecture is one transaction spanning all three modules: posting a goods receipt writes the receipt, the stock ledger rows and a balanced journal entry — or none of them.

How this was built. The architecture is mine: multi-tenancy enforced in the database rather than in application code, the module and permission model, and the decisions recorded below. The implementation was largely AI-assisted — I directed and reviewed it rather than typing it. I've flagged this here rather than in a footnote because the repository makes it obvious, and because the decisions are the part worth discussing.

The problem

Multi-tenancy fails quietly, which is what makes it hard

A multi-tenant application keeps several companies' records in the same tables and is trusted never to show one company another's. The usual implementation is a WHERE tenant_id = ? on every query. It works right up until somebody writes the one query that forgets it — and then nothing breaks. No error is raised, no alert fires. A screen simply renders rows belonging to somebody else, and the first person to notice is a customer.

The trouble with the convention is that it is a convention. Correctness rests on every developer remembering it on every query, forever, including the one added under pressure late on a Friday. There is nowhere to stand and say this is enforced — only a habit, and a code review that has to catch every instance of it.

mini-erp moves the check underneath the application. A handler that forgets its tenant filter returns zero rows, because the database decides what a connection is allowed to see. Forgetting produces an obviously empty screen instead of a silent leak — a failure mode you find in development rather than in an incident report.

Request path, top to bottom.

It is one deployable, not a set of services. That is the whole reason a goods receipt can write into three modules atomically: the moment procurement, inventory and finance become separate services, that single transaction becomes a distributed one — or, more honestly, becomes an eventual-consistency story with compensating writes for the case where the journal entry fails after the stock has already moved. The monolith is the feature.

How a request is isolated, in order

  • The token is verified for its UID, and nothing else. A Firebase ID token proves who signed in. It is never read for roles or tenancy.
  • Identity, tenant and roles are read from the database, every request. Not from a token claim — a claim is a snapshot, and it keeps asserting what was true when it was minted long after an administrator has revoked the access.
  • The handler runs inside a transaction that sets app.current_tenant for that transaction only, via set_config(..., true). The function form is deliberate, because SET cannot take a bind parameter and the alternative is concatenating a UUID into the most security-critical statement in the system. Transaction-scoped, never session-scoped: a session-scoped setting outlives the transaction and would hand the tenant context to whichever request next borrowed that pooled connection.
  • Fourteen tables have row-level security enabled and forced. The policy compares each row's tenant to that setting. FORCE is the part people miss — without it the table's owner bypasses the policy entirely, which silently defeats the mechanism in local development, where you are usually connected as the owner.
  • Both views are security_invoker. By default a view executes with its owner's privileges, which means a view over protected tables cheerfully returns every tenant's rows to everybody.
  • No application role holds BYPASSRLS or SUPERUSER. There is a checked-in verifier that asserts this against a live database — because a role created through a hosting provider's web console quietly gets that privilege, and nothing looks wrong afterwards.
Frontend hiding is cosmetic — a rule, not an aspiration. Every control the interface hides is independently refused by the API. The sidebar without a Finance link and the endpoint that returns module_not_enabled are two separate enforcements of the same fact, and only the second one is load-bearing.
Nothing that represents money is a float. Amounts are NUMERIC(18,2) and quantities NUMERIC(18,4), carried across the wire and through TypeScript as exact decimal strings rather than parsed into a binary float and back. Sums and comparisons happen in SQL, so there is no point in the round trip where a total can quietly acquire a rounding error.

Problems

Three that took real thought

One transaction, three modules — and what happens when it is sent twice

Posting a goods receipt writes three things: the receipt itself, the stock ledger rows, and the journal entry — all in one transaction. The ledger rows and the journal entry are each derived in SQL from the receipt lines, so neither can disagree with what was actually received.

The harder problem is the retry. Somebody receives a delivery on a phone at the warehouse door, the connection drops before the answer comes back, and they press the button again. Two identical requests arrive. Nothing in the data tells them apart from a real second delivery of the same goods — the supplier sent another eighty boxes is an ordinary thing to record, and it looks exactly the same.

So the form stamps each attempt with a one-off id — an idempotency key — created when the screen opens, not when the button is pressed. A resubmit therefore carries the same key as the first try, which is what lets the server recognise it as the same act rather than a new one. Generating the key on the press would give the two attempts different keys and defeat the entire mechanism.

The server then checks that key three times. Each check is there because the one before it can miss:

  • Before doing anything else. This catches the ordinary case — the first request finished, and the user pressed the button again.
  • Again, after locking the purchase order. A retry already in flight can finish while this request is waiting for that lock. Without the second look, this request would then measure the delivery against quantities its own duplicate had just recorded, and reject it as an over-receipt — telling somebody to go and correct a quantity that was in fact recorded perfectly a moment earlier. A test is named for this case, and it failed on exactly that misleading error before the second check existed.
  • At the insert itself. A unique constraint on the key has the last word, for a duplicate that commits in the sliver of time between the second check and this write.

That third one needs care, and it is where the savepoint comes in. In PostgreSQL a statement that fails normally takes the whole transaction down with it — so once the insert is rejected, you can no longer use that transaction to go and fetch the receipt the duplicate created, which is the one thing you now want to do. The insert is therefore wrapped in a savepoint: an undo point inside the transaction. When the constraint fires, the code rewinds to that point rather than losing the transaction, reads the original receipt, and returns it.

The savepoint covers the receipt-number allocation as well, so the number the rejected attempt had claimed is handed back instead of being spent. Otherwise every retry would leave a permanent hole in that workspace's receipt numbering — GR-0004, GR-0007, and nothing to explain where the ones in between went.

What the person at the warehouse door sees is one line: GR-202607-0005 had already been posted. Their delivery was counted once.

You cannot approve your own work — including as the admin

Segregation of duties is easy to state and easy to quietly undermine. The clause that matters is the second one: the rule applies to the workspace administrator too. That is the natural place to carve an exception — the administrator is trusted, and they are usually the one unblocking somebody else — and it is exactly the exception that makes the control worthless.

It is checked per record, which is also why it cannot live in the role middleware alongside everything else. The middleware knows the caller's level; it does not know who raised the document in front of them. Status is checked first, deliberately: telling somebody "you may not approve your own" when the real answer is "it was approved yesterday" sends them to argue with the wrong person.

Deleted rows still have to appear in history

Soft deletion is easy to get half right. Lists filter deleted rows and writes refuse them — but the stock ledger's join to the product table carries no deleted filter at all, on purpose. A movement of a product somebody deleted last week is still a movement that happened, and adding AND p.deleted_at IS NULL there by reflex would not hide a stale product; it would erase last quarter's history from the screen.

That join looks exactly like an oversight, which is the problem. It carries a comment saying it is deliberate and a test that fails if someone "fixes" it — the only two things that stop a reasonable-looking code review from reintroducing the bug.

Delivery

Infrastructure and operations

Backend

Go with Fiber, built as a modular monolith — three modules, one deployable. Containerised; the image builds and runs. Memory safety, a small container surface and static typing are what the language buys here.

Identity

Firebase Authentication issues the token; the API verifies it for the UID alone. Everything about what that person may do is read from the database on the same request that uses it.

Tests & CI

Operability

A checked-in verifier (cmd/dbverify) asserts the invariants that live in the database rather than in Go, against whichever database it is pointed at — the ones a test suite running on a container can never confirm about production.

What I'd build next, in order

  • The audit log. Designed and specified during the MVP and deliberately not created — the tables are described, the write path is not. First job, because it is the thing an ERP is asked about first.
  • Reversal documents. Ledger corrections are currently new adjustment entries with a note. A first-class reversal that points at what it reverses is the difference between a correction and an explanation.
  • Make the desktop screens as capable as the API behind them. The clearest remaining weakness, and the gaps all have the same shape — the server already does the work, and the interface never asks for it. Sorting: every list endpoint sorts, by an allowlisted column with a tie-broken ORDER BY so rows cannot swap between pages — but each screen sends one fixed order and no column header is clickable, so a list cannot be reordered by the person reading it. Addressability: search, supplier and the page number live in component state rather than in the URL, so a narrowed view cannot be bookmarked, shared or recovered with the back button. Two places already prove the pattern: the confirmation panel's ?sourceId= links, and the dashboard tiles, whose ?status= the requisition list now reads on arrival — it is seeded from the URL, not bound to it, so changing the dropdown afterwards still does not rewrite the address. Density: the layout switches between phone and desktop and offers nothing in between, so a wide screen leaves a third of its width empty whatever page size is chosen. Bulk actions, keyboard navigation and saved filter views belong in the same pass.
  • Approvals beyond one level. Value thresholds, delegation, and multi-step chains — the three things every real procurement department asks for immediately.
  • Finance past the stub. Invoicing, the payment cycle, and period close. The posting side already works; what's missing is everything that happens after.
